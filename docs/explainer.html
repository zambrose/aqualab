How AquaLab works

Written for engineers who are comfortable with code but new to AMMs and DeFi. We build from first principles — what an automated market maker is, the curve math, fees and MEV — then show how 1inch's SwapVM turns all of that into a composable bytecode program, which is what AquaLab demonstrates and visualizes. Every section is short; worked numbers are illustrative unless marked as demo values.

1Why AMMs exist

A traditional exchange runs an order book: buyers and sellers post limit orders and a matching engine pairs them. That needs active market makers constantly quoting, and it's expensive to run fully on-chain (every order placement/cancel is a transaction).

An Automated Market Maker (AMM) replaces the order book with a formula and a pool of reserves. Liquidity providers (LPs) deposit two tokens; a fixed function decides the price for any trade against those reserves. No counterparty needs to be online — you trade against the math. This is what made on-chain spot trading practical (Uniswap, 2018).

Mental model

An AMM is a vending machine for token swaps: it always quotes a price from its current inventory, and each purchase shifts the next price. The "strategy" is the pricing function.

2Constant product & slippage

The canonical AMM is the constant-product market maker: keep the product of the two reserves constant across a trade.

x · y = k        (x = reserve of token A, y = reserve of token B)
spot price of A in B = y / x

To swap in Δx of token A, you solve for the output Δy that keeps k fixed:

// pool: 1000 WETH and 3,000,000 USDC  →  k = 3,000,000,000, spot = 3000 USDC/WETH
add 1 WETH      → x' = 1001
y' = k / x'     = 3,000,000,000 / 1001 = 2,997,002.998 USDC
amountOut       = y − y' = 3,000,000 − 2,997,002.998 = 2,997.0 USDC

You paid 1 WETH and got ~2997 USDC, not the full 3000. The missing ~3 USDC is slippage (a.k.a. price impact): the bigger your trade relative to the pool, the worse your average price, because the curve moves as you traverse it. This is a feature — it's what keeps the pool from being drained and what arbitrageurs use to keep the price in line with the wider market.

The invariant that matters

A correct constant-product swap never lets k decrease — rounding always favors the pool (the maker). AquaLab fuzz-tests exactly this: "k is non-decreasing across an exact-in swap."

3Concentrated liquidity

Plain x·y=k spreads liquidity across all prices from 0 to ∞ — but almost all trading happens near the current price, so most of that liquidity sits idle. Concentrated liquidity (Uniswap v3's big idea) lets LPs put their capital into a chosen price band [P_min, P_max]. Inside the band the pool behaves like a much larger constant-product pool, so trades get a better price for the same real capital.

Mechanically, it works via virtual reserves: from the real balances and the band, you compute a liquidity depth L and price as if the reserves were larger:

x_virtual = x_real + L / √P_max
y_virtual = y_real + L · √P_min
amountOut = Δin · y_virtual / (x_virtual + Δin)
Demo value

In AquaLab's fork test, the concentrated pool returns 2996.67 USDC for the same trade where a plain x·y=k pool returns 2961.47 — the band genuinely deepens the book.

4Fees & LP economics

Why would anyone provide liquidity? Trading fees. Each swap pays a small fee (e.g. 0.30%) that accrues to LPs. In SwapVM's flat-fee instruction, the fee is taken off the input before the curve prices it: the taker pays the full input, the curve only credits output for the post-fee amount, and the difference stays in the pool for the maker.

netIn = Δin − ⌈Δin · feeBps / 1e9⌉     (rounding up favors the maker)
amountOut = price(netIn)                // curve sees the smaller input

Fees are also the LP's compensation for impermanent loss — the opportunity cost of holding a volatile pair in a pool versus just holding the tokens. (Out of scope here, but it's the other half of LP returns; see the resources.)

5MEV, decay & virtual balances

MEV (Maximal Extractable Value) is profit a block producer — or anyone who can order transactions — extracts by inserting/reordering trades. The classic attack on an AMM is the sandwich: a bot sees your pending swap, buys ahead of you (pushing the price up), lets your trade execute at the worse price, then sells right after for a profit — paid for entirely by your slippage.

1inch's Mooniswap pioneered a defense using virtual balances that decay over time. After a trade, the pool doesn't instantly show the new price to the next trade; instead it keeps a decaying "offset" so the price recovers gradually over a window. A sandwich's second leg has to fight that lingering offset, which erodes the attacker's edge and redirects slippage value back to LPs.

offset(t) = offset₀ · (expiry − t) / period      // linear decay to zero
while it persists, it virtually shrinks balanceOut / grows balanceIn
Demo value

AquaLab's third trace is a follow-up swap arriving while a prior trade's offset is two-thirds un-decayed (1200s into a 3600s window). You can watch the decay instruction shift the virtual reserves before the curve prices the trade — visible, on-screen MEV protection.

6SwapVM: an AMM as a bytecode program

Here's the leap that makes 1inch's design different. Instead of each AMM being a hardcoded contract, SwapVM is a tiny virtual machine, and a "strategy" is a program of instructions it executes. The pricing logic above — constant product, concentration, fee, decay — are opcodes you compose.

A program is a byte stream of triples

[ opcode ][ args_length ][ args ]   ·   [ opcode ][ args_length ][ args ]   ·   …

AquaLab's composed program:
  _salt(8B)  →  _decayXD(2B)  →  _flatFeeAmountInXD(4B)  →  _xycConcentrateGrowLiquidity2D(64B)

Five registers, mutated by instructions

The VM carries a small register file — the SwapRegisters — that instructions read and write. The taker specifies one amount; the VM computes the other; instructions mutate the registers along the way:

RegisterMeaning
balanceIn(virtual) reserve of the token being sold
balanceOut(virtual) reserve of the token being bought
amountInamount of input token
amountOutamount of output token
amountNetPullednet pulled (used by protocol-fee accounting)

Crucially, instructions only compute amounts. The actual token transfer — the maker↔taker settlement — happens once, in the VM, after the instruction loop finishes. This is why ordering is safe to reason about: the loop is pure arithmetic on registers; money moves at the end.

Wrappers vs leaves

Fee and Decay are wrapper instructions: each adjusts the registers, calls runLoop() to execute the rest of the program, then post-processes on the way back out. The AMM is a leaf that sets the missing amount and returns. So byte order encodes nesting: Decay( Fee( Swap ) ). Both wrappers assert the swap hasn't priced yet, so the curve is forced innermost — putting it first reverts.

quote() must equal swap()

SwapVM exposes quote() (a read-only preview) and swap() (execution). With identical taker input they must return identical (amountIn, amountOut) — otherwise a preview would lie. AquaLab asserts this on the Aqua path and surfaces a quote == swap ✓ badge in the visualizer.

7Aqua: shared liquidity

A SwapVM strategy needs reserves to price against. There are two ways to supply them, running the same strategy bytecode:

  • Dynamic balances — the maker signs the strategy off-chain (EIP-712); reserves are internal to SwapVM. Good for isolated, single-maker strategies.
  • Aqua — the maker ships liquidity into the shared Aqua contract, sets a flag (useAquaInsteadOfSignature), and omits the balance instruction (Aqua manages balances). Aqua is a non-custodial shared liquidity layer: many strategies draw on pooled, on-chain liquidity.

The bounty is "Build an Aqua App," so AquaLab demonstrates the Aqua path: it ships into the live Aqua deployment and lets a taker swap through it, with real token transfers on a mainnet fork.

8How AquaLab composes it

Putting the pieces together, AquaLab:

  1. Builds a composed program — salt → decay → fee → AMM — with the concentrated-liquidity opcode as the primary curve and constant product as a fallback.
  2. Ships it into live Aqua on a mainnet fork and runs a real taker swap, asserting the transfers, quote()==swap(), and curve invariants (including the upstream 1inch CoreInvariants).
  3. Exports the execution as a trace and renders it in a web debugger: the instruction pipeline, the five SwapRegisters mutating per step, the balance deltas, and the animated price curve.
A real-world wrinkle we surfaced

The SwapVM router deployed on mainnet is a newer build than the latest published source tag, with extra opcodes and a shifted opcode table — so program bytes built against the pinned source can't execute on it. AquaLab handles this honestly: it executes on a self-deployed engine from pinned source (for reproducibility) while using the real live Aqua liquidity, and a test proves on-chain that the canonical router is live and points at the same Aqua. Engaging with that dev-preview reality is part of the point.
