The idea

AMMs are usually monolithic.
SwapVM makes them composable.

A 1inch SwapVM strategy isn't a fixed curve — it's a program of instructions. You assemble a pricing primitive, a fee, and MEV protection as separate opcodes that wrap each other.

We ship a composed position — concentrated liquidity + progressive-cost fee/decay — into the real, deployed Aqua contract, and make every instruction step visible.

The instruction pipeline

Four opcodes, nested by byte order

Controls._salt
unique strategy hash · no-op
Decay._decayXD
MEV protection · virtual-balance decay
outer wrapper
Fee._flatFeeAmountInXD
LP fee on input amount
inner wrapper
XYCConcentrate._xycConcentrateGrowLiquidity2D
concentrated CPMM · prices the trade
leaf
Bytes encode execution nesting: Decay( Fee( Swap ) ). Both wrappers assert the swap hasn't priced yet — so the order is enforced by the protocol, not by convention.
The opcodes — and why each is there
OpcodeWhat it doesWhy it's in the program
_xycConcentrate
GrowLiquidity2D		Concentrated CPMM — focuses liquidity into a sqrt-price band via virtual reserves.Deeper book near spot → better price than plain x·y=k at equal reserves.
_flatFee
AmountInXD		Takes a bps fee off the input before the curve prices it.LP revenue; the pool keeps full input but pays out less, so k grows extra.
_decayXDA trade leaves an offset that linearly decays over a window.MEV / sandwich protection — the attacker's second leg eats the decay penalty.
_saltPricing no-op.Makes otherwise-identical pools ship as distinct immutable Aqua strategies.
Honest course-correction: the originally-planned _progressiveFeeInXD isn't in the Aqua opcode table. We read the real sources, used the opcodes that exist, and realize progressive behavior via fee tiering + decay — documented, not faked.
